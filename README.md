# LiveMockup

**在 3D 样机里跑一个真网页，把你的操作录成关键帧，回放时网页自己动起来，最后导出成产品演示视频。**

和 iMockup 那类工具的根本区别：**不用上传截图**。样机里装的是一个真的、可交互的网页（本地反代 + 注入运行时），你点它、划它、切 tab，每一个动作都变成一个带时间戳的关键帧；回放时工具按时间轴重新「跑一遍」这些操作，网页状态是真的在变——搜索框真的出结果、购物车真的累加、页面真的跳转。

页面实在没法代理演示时（登录墙、canvas 视频、原生 App 界面），还有 **录屏视频模式**：把你的录屏塞进样机屏幕里播，时间轴和镜头运镜照样工作，机型可以「自适应输入分辨率」。

零依赖：只用 Node 内置模块 + 原生 Web API，无构建、无 npm 包。

---

## 运行

```bash
cd live-mockup
node server.mjs        # 或 npm start
```

打开 <http://localhost:4321>。默认端口 4321，可用 `PORT=5000 node server.mjs` 改。建议用 Chrome / Edge（导出要用 `getDisplayMedia`）。

## 三步做出片子

**1. 选页面**
左侧内置两个可交互演示，点一下就载入：

| 预设 | 内容 | 场景 |
| --- | --- | --- |
| Kopi 咖啡点单 | 移动端 App：搜索、加购、数量、轮播 tab | 手机 · 9:16 · 极光背景 |
| Aurora 产品官网 | 桌面官网：定价切换、FAQ、注册弹窗 | 浏览器 · 16:9 · 影棚背景 |

也可以把顶栏换成任意 `http(s)` 网址——会走本地反代载入，同样能录操作。

**2. 点「录制操作」，然后在样机里真的操作它**
每次点击 / 输入 / 选择 / 滚动 / 跳转都会落到下方时间轴的动作轨上，按真实时间排布。再点一次停止，自动定位成一条时间轴。

**3. 排镜头 + 导出**
- 拖舞台空白处 = 环绕旋转，滚轮 = 推拉，双击 = 复位（`.` 键也能复位）。
- 右侧「镜头预设」一键生成 推向特写 / 侧身环绕 / 悬浮上移 / 呼吸定格。
- 勾选「拖动舞台时自动更新关键帧」，随便摆几个机位就是一个运镜。
- 点「导出视频」。**两种模式两条路，差别很大**：
  - **录屏视频模式 = 离线逐帧渲染**（推荐）：不弹共享窗口，不碰屏幕捕获。工具把背景、样机外壳、屏幕里的视频帧逐帧合成到一张离屏 canvas 上，按镜头做透视投影贴回去，再用 WebCodecs 的 VP9 编码器按**精确时间戳**编码，由自带的 WebM 封装器写成文件直接下载。
    导出时主界面会被**冻结**，弹窗显示 `当前帧 / 总帧数`、导出速度（fps）、已用 / 剩余时间，以及正在合成那一帧的缩略图；`Esc` 或「取消导出」随时中止。**每帧都会渲染完再走下一帧，不丢帧**。
  - **网页模式 = 屏幕捕获**：iframe 的像素浏览器不给读（同一次文档的跨源限制），只能捕获标签页。弹窗里选**「此标签页」**，工具按舞台矩形裁切、重绘到 1080×1920（或 1920×1080）。30fps 编码，比重在 60fps 时轻一半。这条路必须实时录标签页，所以**不能**弹遮罩（会被录进画面），进度仍显示在按钮上。

所以想要**完全离线、可重复、不依赖窗口大小**的成片，走录屏视频模式。

工程会自动存进 localStorage；「保存 JSON / 导入」可以带走或分享（只存时间轴与场景，不存网页内容）。

## 录屏视频模式

如果页面本身没法被代理演示（登录墙、canvas 视频、原生 App 界面……），可以走另一条路：**把你录好的屏放进样机屏幕里播**。

把顶栏左边的模式切到「录屏视频」，然后：

- 把 `.mp4 / .webm / .mov` **拖进左侧虚线框**，或者点它选文件；也可以直接粘贴视频直链（`https://.../demo.mp4`）。
- 样机屏幕上直接播这段视频，**时间轴和镜头轨照常工作**：镜头围绕屏幕做运镜，导出时一起录进画面。
- 机型自动切到 **「自适应」**，画幅自动切到 **「自适应 · 按输入分辨率」**——样机的长宽比直接等于你的视频分辨率，不会被拉伸或留黑边。想回手机/平板外观随时点回去（自适应只在录屏模式下可选）。
- 时间轴总时长自动取视频时长（上限 120 秒）。

两个实现细节值得知道：

- **视频当时间轴**：播放时每一帧都读 `currentTime` 反推播放头位置，所以拖动时间轴、暂停、循环都不会音画不同步；反过来拖播放头也会把视频定位到对应帧。
- 浏览器录屏（MediaRecorder）产出的 WebM 常常把时长报成 `Infinity`，工具会先「探一次真实长度」再填时间轴——这就是为什么你自己录的片子拖进来时长是对的。

录屏模式下的本地文件不会被记住（浏览器不给页面持久化文件路径），重开页面时左侧会提示重新选一次；时间轴和镜头关键帧都还在。视频直链则可以自动重连。

## 关键帧系统

时间轴有两层：**镜头轨**（机位，菱形标记）和**动作轨**（网页操作，胶囊标记）。选中镜头关键帧后，右侧检视器会变成它的面板：

| 区域 | 能做什么 |
| --- | --- |
| 顶部读数 | 播放头时刻、当前处在哪一段、段内进度，以及此刻实际机位 |
| 七个滑块 | 水平 / 垂直 / 进深 / 偏航 / 俯仰 / 旋转 / 缩放，拖动即所见（播放头不在该帧会自动跳过去） |
| 时间 + 对齐 | 精确改帧时间；「对齐」把这一帧挪到播放头 |
| 缓动预设 | 线性 / 缓入缓出 / 缓出 / 缓入 / 回弹 / 强缓动 / 快切，共 7 条标准曲线 |
| 曲线编辑器 | 直接拖两个控制手柄做**自定义 cubic-bezier**，下面的读数实时显示 `cubic-bezier(x1,y1,x2,y2)` |
| 保持 | 勾上就变成阶梯：整段保持起始姿态、到下一帧瞬切（做「定点不动然后弹一下」很省事） |
| 跳到 / 复制姿态 / 粘贴姿态 | 把某个机位搬到另一帧，不复制时间 |
| 复制帧 / 删除 | 复制一帧（落在 +0.2s）/ 删除选中 |
| 全部关键帧 | 帧列表，点任一行直接选中并跳到该帧 |

时间轴上的操作：

- **拖动**标记时先磁性吸附到其它关键帧和播放头，吸不上就落到 0.05s 网格，并显示一条参考竖线；
- **Shift 点击**加选（可多选，`Delete` 一次全删）；
- **双击**标记 = 跳到该帧（动作条双击还会顺便把网页重放到那一刻）；
- 勾着「自动更新关键帧」在舞台拖动时：播放头 0.12s 内已有帧就**就地更新**它，否则**新插一帧**——不会像以前那样悄悄改掉旁边的帧。

### 缩放与框选

时间轴右上角是缩放组：`−` / 缩放倍数（点它回到全览）/ `＋`。放大后只会渲染窗口内的标记，刻度会自动细分到 0.5s、0.25s、0.1s……

| 操作 | 效果 |
| --- | --- |
| `Ctrl/Cmd` + 滚轮 | 以鼠标位置为锚点缩放（1× ~ 24×） |
| 滚轮 | 缩放后左右平移时间轴 |
| 在轨道**空白处拖动** | 拉出矩形框选，框里的帧实时高亮；松手即选中（`Shift` 并入已有选择） |
| 在轨道空白处**单击** | 定位播放头 |
| 在**刻度尺**上拖动 | 拖动播放头，方便逐帧对位 |

框选出来的多选可以直接拖其中任意一个标记整体平移、`Delete` 整批删除、或点「复制帧」整批复制。

## 任意网址是怎么跑起来的

浏览器不允许把 iframe 的像素画进 canvas，也不让跨站页面被随意嵌入。所以 `server.mjs` 做了一层反代：

```
/p/<原始完整 URL>
```

- 剥掉 `X-Frame-Options` / `Content-Security-Policy` / `COEP` / `CORP` / `integrity` / `<base>` / `meta refresh`；
- 把根相对路径、绝对 URL、`srcset`、`url()`、`@import`、没加引号的属性值（`src=/a.js`）统一改写成 `/p/<abs>`；
- 3xx 的 `Location` 也重写成 `/p/<abs>`，于是跳转后仍在代理里；
- 往 `<head>` 注入 `/js/agent.js`——被演示页里的运行时，负责录制事件、执行回放动作、画点击涟漪。

### 本地开发服务器（Vite / Next / CRA）也能直接贴

前端常自己发根相对请求（`fetch('/api/x')`、`new Image().src='/a.png'`、`import('/src/x.js')`），这些 URL 是在 JS 里拼的，重写 HTML 抓不到，于是会打到编辑器自己的 origin 上——**表现就是「页面在、数据和图片没了」**。现在有三层兜底：

1. `localhost` / `127.0.0.1` / `*.local` / 裸 IP 输入时不写协议，**默认补 `http://`**（dev server 一般没有证书，补 https 会直接 502）；
2. 静态目录里找不到这个路径时，看 `Referer` 里有没有 `/p/<目标>`，有就把这个请求也转发过去——`fetch('/api/items')`、JS 里创建的 `<img>`、代码分割的 `import()` 都因此恢复；
3. 注入的运行时会把**指向目标站点自身的绝对 URL**（`http://localhost:3000/api/x`）拉回 `/p/` 同源路径，绕过目标站点没发 CORS 头的问题。

还没通的：WebSocket（HMR 会一直报重连，不影响页面）、Service Worker、vite 的 HMR 热替换。

## 导出机制：为什么放弃实时渲染

旧版是「边播边合成」：渲染跟着墙钟跑，一帧超过 33ms 就直接丢掉，成片里就是跳帧卡顿。
现在整条链路按**帧号**走，不跟墙钟：

1. 第 i 帧固定对应时间 `i / fps`，先把 `<video>` 精确定位到那一刻（等 `seeked` 回来），拿到的一定是那一帧；
2. 合成：背景（只补脏区）→ 预模糊阴影 → 样机外壳 → 屏幕内容 → **按镜头做透视投影**贴回；
3. 交给 `VideoEncoder`，时间戳就是 `i / fps` 微秒，每秒一个 keyframe；
4. 编码队列堆太多就等会儿，然后才走下一帧。

慢就是慢，但**一帧都不会丢**，成片时长严格等于时间轴时长（2 秒的片子就是 2.000 秒，
和渲染花 4 秒还是 40 秒无关）。速度显示在弹窗里：快机器十几到几十 fps，慢机器几 fps，
差别只是「要等多久」，不影响成片。

单帧成本大致三份：**解码定位**（seek 回关键帧再解到目标，30~60ms）、
**合成**（10~20ms）、**编码**（异步，不占主线程）。所以导出期间主界面是冻结的：
遮罩吃掉全部输入，编辑器整体从合成树里摘掉，不和渲染抢 CPU —— 每让出一次主线程，
浏览器就要重画一遍 3D 舞台，这笔账在 headless / 集显机器上很贵。

编码走 WebCodecs（`VideoEncoder`）+ 自带的极小 WebM 封装（`public/js/webm-muxer.js`，
EBML / Cluster / Cues 全手写，零依赖）。WebCodecs 需要安全上下文：`localhost` 可以，
用局域网 IP 的 http 打开就没有 —— 这时自动退回实时录制，弹窗会写明「可能丢帧」。

## 场景级设置：机型 / 屏幕比例 / 输出比例

这三样属于**场景**，不属于关键帧 —— 整段视频只有一份，关键帧里只存机位
（`x y z rx ry rz scale t ease`）。预览（CSS 3D）和渲染（WebGL）都从同一份取景规则出发：

| 项 | 来源 | 预览与渲染怎么保持一致 |
| --- | --- | --- |
| 机型 | `project.device`（手机 / 平板 / 浏览器 / 自适应） | 同一张边距表 `Stage.FIT_MARGIN`（0.84 / 0.84 / 0.9 / 0.88） |
| 屏幕比例 | 自适应机型 = 输入视频分辨率；其它机型 = 机型设计尺寸 | 都调 `Stage.fitOf(model, 设备尺寸, 画框尺寸)`，只有一份实现 |
| 输出比例 | `project.aspect` | 舞台方框和输出画布同一个长宽比，取景只差整数取整（实测 0.13%） |

### 机位单位（v2）：相对画面，而不是相对窗口

关键帧里只存机位，单位是**画面比例**，所以同一个工程在任何窗口、任何缩放、任何机器上构图都一样：

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| `x` | 画框**宽度**的比例 | `0.33` = 往右 33% 画宽 |
| `y` | 画框**高度**的比例 | `0.177` |
| `z` | **透视距离**的比例 | `0.294` = 往前推到透视距离的 29% |
| `scale` | 倍数 | `1.21` |

透视距离也不再写死 `1700px`，而是 `1700 / 582 × 画框高度`：
参考画框（582 高）仍是 1700px，1080 高的成片画布是 3155px ——
和以前「1700 按舞台等比放大」的结果一致，但不再依赖窗口高度。
预览（`Stage.apply`）用同一套公式换到舞台像素，导出（`Render.render`）换到输出画布。

> v1 的老工程（`x/y/z` 是编辑器舞台像素）在导入时会**一次性换算**成比例，
> 换算用固定的参考画框 1036×582，和打开时的窗口大小无关；面板读数随之变成
> 「成片画布上的 px」。换算是幂等的，存回去就是 v2。

玻璃反光（`glare`）也按编辑器的 `.device__glare`（118° 线性渐变 + 顶部径向高光、
screen 混合、opacity .9）画进样机贴图，所以开着反光也不会出现「预览有、成片没有」。

`npm run test:parity` 就是守这件事的：读编辑器真实的 `matrix3d` / `--fit` / `perspective`
和渲染侧公式逐个角对比，并用「同机位截图 vs 渲染帧」的逐像素差兜住装饰类差异
（普通机位目前 ≤1.4px 角差、MAD ≈4）。

## 透视贴图为什么用 WebGL

canvas 2D 没有梯形贴图，只能把样机切成小格、每格用仿射近似透视。
而仿射逼近的误差 ∝ 格宽² × 透视强度：**偏航一大，误差会迅速放大到肉眼可见**。
实测（1080p 输出、机身占屏约 1350px 宽）：

| 偏航 | 12×12 网格单格误差 | 观感 |
| --- | --- | --- |
| 0° | ~0.1px | 正常 |
| 30° | 3.5px | 横线开始有台阶 |
| 60° | 8.6px | 横线被切成一段段、文字错位 —— 就是「画面被撕裂」 |

想靠加密网格压到亚像素要 3000+ 格（每格一次 `drawImage`），代价不可接受。
所以改成把四个角的**齐次坐标**交给 GPU，让它自己除 w 并做透视校正插值：

```
screen = (X/w, Y/w),  w = (PERSP - Z)/PERSP
gl_Position = (2X/W, -2Y/H, 0, w)   // 除完就是 NDC；几何精确，没有格子就没有接缝
```

顺带两点：
- 被镜头压到很窄的那一侧是强缩小采样，只靠双线性会闪 —— 这时自动开 mip 链（+ 各向异性过滤）；
- 背景是静态贴图，机身/阴影只覆盖脏区，用 `scissor` 限定重绘范围。

WebGL2 不存在时（极少数环境）自动退回 canvas 2D 逐格仿射，网格比旧版更密（20×20），
撕裂会轻一些但仍然只是近似 —— 弹窗「输出」一行会写明当前用的是 `WebGL` 还是 `2D`。

## 用独显跑（双显卡机器）

浏览器默认按「省电」给 WebGL / canvas 挑适配器，双显卡笔记本上通常落在集显，
于是渲染时核显 100%、独显 0%。**代码这边每个上下文都显式请求了高性能适配器**：

- WebGL2：`getContext('webgl2', { powerPreference: 'high-performance', ... })`，失败才退 `default`；
- canvas 2D：`getContext('2d', { powerPreference: 'high-performance' })`（不支持的浏览器自动忽略）；
- 编码器：`VideoEncoder.configure({ hardwareAcceleration: 'prefer-hardware' })`，拿不到才退回不指定；
- 脚本加载时先用 `navigator.gpu.requestAdapter({ powerPreference: 'high-performance' })`
  把 dGPU 唤醒一次，顺带读出适配器名字。

**自检**：浏览器控制台会打印一行

```
[LiveMockup] GPU 请求 = high-performance · 实际适配器 = ANGLE (NVIDIA GeForce RTX ...) · 判定 = 独显
```

也可以随时在控制台执行 `Render.gpu` 看完整字段（`adapter` / `kind` / `discrete` / `hwEncode` / `backend`）。

**页面做不到的部分**（这三层任意一层反着来，都会把上下文压回集显）：

1. Windows 设置 →「系统 → 显示 → 图形」里把浏览器指定成「节能」；
2. NVIDIA 控制面板 →「管理 3D 设置 → 程序设置」选成「集成图形」；
3. 用 `--force_high_performance_gpu` 启动的浏览器可以被反向覆盖。

反过来，想 100% 强制全进程走独显，用 Chromium / Edge 加启动参数
`--force_high_performance_gpu` 最干净（不受系统设置左右）。

没有独显的机器不需要任何操作：`high-performance` 只是个偏好，退化成集显也不会失败。

## 导出清晰度

两条路的清晰度来源完全不同：

**录屏视频模式（内部渲染）** —— 与屏幕、窗口大小**无关**。输出长边固定 1920，样机贴图分辨率按**投影后在画面上占多少像素**算（约 1.1 倍超采样，上限 2.6×），所以：

- 窗口多小都不影响画质，甚至可以在别的地方干别的事；
- 镜头推得越近，贴图自动越清晰（不会像固定倍率那样糊）；
- 锐度上限取决于输入视频本身（1280×720 的录屏放到 1920 宽画布上不会凭空变清晰）；
- 想要更锐利，就把录屏按更高分辨率录。

**网页模式（屏幕捕获）** —— 舞台在屏幕上有多大，决定输出有多锐利：

- 导出时工具会自动收掉侧栏、时间轴、脚注，让舞台吃满窗口（最大化窗口收益很大）；
- 在 HiDPI（2×）屏幕上捕获的物理像素本身翻倍，接近 1:1，明显更清晰；
- 16:9 画幅在 1080p 屏幕上基本是 1:1；9:16 因为是竖向，受窗口高度限制，会做约 2 倍放大。


## 已知限制

- **反代不是万能的**：依赖 `X-Frame-Options: deny` 以外策略、Service Worker、`window.top` 判断、OAuth 弹窗的站点可能载入不完整；登录态需要在该站点自己的域名下先登录（反代域不同，cookie 不通）。
- **本地 dev server 用 `http://`**：如果它开了 HTTPS 自签证书，Node 端会校验失败、代理返回 502，改成 http 起或者临时关掉 https 即可。
- **回放是「重跑操作」而不是录屏**：网页若依赖随机数、时间、真实网络请求，回放结果可能和你录的那一次不完全一致（这正是本工具相对截图的优势，也是它必须遵守网页真实逻辑的原因）。
- **跨域跳转到某个不允许多次请求的接口**，回放时可能比录制时慢；回放等 `hello` 握手最多 15 秒。
- 网页模式的导出受屏幕捕获分辨率影响，见上文「导出清晰度」。要摆脱这个限制就用录屏视频模式。
- **网页模式的导出必须屏幕捕获**：iframe 里的像素读不到（跨源语义），canvas 拿不到，所以那条路省不掉「选择共享对象」这一步。录屏视频模式没有这个限制。
- **录屏模式只认浏览器能解的编码**：mp4(H.264) / webm(VP8/VP9) / mov 一般可以，`.mkv`、部分 HEVC、以及带 DRM 的源会直接报「格式不支持」。视频直链还要求对方允许跨站播放（不发 `Access-Control` 限制即可，`<video>` 本身不强制 CORS）。
- 录屏模式的本地文件不会被持久化（浏览器不允许页面记住文件），重开页面需重新选一次。
- **内部渲染是离线逐帧的，比实时慢**：成片时长精确、不丢帧，代价是要等（速度见弹窗里的 fps）。12 秒的片子在普通机器上大约要十几到几十秒。
- **导出期间主界面被冻结**：这是刻意的（任何交互都会混进成片，还会抢渲染的 CPU）。要改东西就先点「取消导出」。
- **离线编码依赖 WebCodecs**（需要 https 或 localhost）。用局域网 IP 的 http 打开时会退回实时录制，那条路可能丢帧，弹窗里会写明。
- **透视合成优先走 WebGL2**：没有 WebGL2 的环境会退回 canvas 2D 逐格仿射，大偏航仍可能出现轻微撕裂（弹窗「输出」一行会显示 `2D`）。
- 仅 Chrome / Edge 系。
